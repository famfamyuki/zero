# AgentGraph Studio — Data & AI Governance

Status: **Authoritative cross-cutting governance**  
Scope: User data classification, persistence/retention, AI-provider boundaries, evaluator change management, privacy, export/deletion direction, and consent-sensitive use.

This document does not expand the active implementation packet. It defines rules that future persistence, history, runtime evidence, account/cloud, and AI work must satisfy.

## 0. Core rule

AgentGraph Studio should collect/store/send only what is necessary for the selected product capability.

User-owned source/runtime means the product must not quietly turn private workflow content into a hidden platform asset.

---

# 1. Data classes

Treat at least these classes separately:

## A. Public/product configuration

Examples:

- public templates
- product docs
- version constants

## B. Operational metadata

Examples:

- deployment/version
- bounded error category
- request latency
- contract version

Must not be used as a reason to include raw workflow content.

## C. User workflow source

Examples:

- roles/goals/backstories
- task descriptions
- output contracts
- tool configuration
- imported project semantics/source

Default: private user content.

## D. Derived Evidence / evaluation artifacts

Examples:

- deterministic Evidence
- inferred intent
- Architecture Review findings
- proposals
- semantic diffs

These remain user-derived content even when generated by AgentGraph.

## E. Runtime evidence

Examples:

- traces
- actual tool calls
- latency/cost records
- errors
- side effects
- approvals

Potentially higher sensitivity than design-time data; ingestion must be explicit and scoped.

## F. Secrets / credentials

Never treat as ordinary workflow content. Minimize collection and avoid persistence/analytics/logging unless a narrowly specified secret-management feature exists.

---

# 2. Persistence default

Do not add persistence merely because a feature could benefit from history.

A packet that introduces persistence must define:

- exact persisted object
- storage location
- purpose
- identity/version contract
- retention behavior
- deletion behavior
- export behavior
- migration/backward compatibility
- privacy/security boundary
- offline/local/cloud behavior

Current non-persistent features must not be silently upgraded to cloud persistence by unrelated work.

---

# 3. Local-first / user ownership

Where product value permits, preserve a path for user-owned/local project artifacts.

Cloud sync/collaboration may be additive. It must not redefine local source ownership or make export impossible.

A future workspace design should distinguish:

- local project persistence
- browser-local convenience state
- optional account/cloud sync
- team/shared state

These are different trust and durability levels.

---

# 4. Retention, deletion, export

Before durable cloud storage of workflow-derived content, define:

- default retention or durable-until-deleted semantics
- user deletion behavior
- project/account deletion behavior
- backup/tombstone implications where applicable
- export format
- relationship between deletion and shared/team copies where applicable

Do not promise immediate physical erasure from all infrastructure unless the implemented storage system actually guarantees it.

---

# 5. Analytics boundary

Existing analytics is a protected product behavior, but analytics must remain metadata-minimal.

Do not send by default:

- workflow text/source
- Evidence content
- imported code
- prompt text
- AI response/findings
- node/edge identifiers
- secrets
- runtime trace bodies

Use bounded categorical properties where possible.

Product-quality measurement must not require leaking user content.

---

# 6. AI provider disclosure and minimization

Before sending workflow-derived information to an AI provider:

- invocation must match the specified user action/feature
- disclose that necessary workflow-derived content is sent when required by the UX contract
- send the minimum sufficient representation
- omit secrets/tool parameter values where not needed
- alias internal identifiers where sufficient
- do not send unrelated UI/analytics/presentation state
- use provider storage/training controls according to the active provider contract and packet

Provider changes must not silently broaden what user data is transmitted.

---

# 7. Provider/training use

Private user workflow content, Evidence, evaluation output, imported source, and runtime evidence must not be described or used as a hidden training moat without an explicit, documented policy and appropriate user consent/legal basis.

Strategic value should come from product contracts, evaluation methodology, curated consented/public fixtures, and user-specific history that benefits that user—not undisclosed extraction of private content.

---

# 8. Evaluator Change Management

A production evaluator is versioned behavior, not merely a model environment variable.

Material changes include:

- model/provider
- system/reviewer prompt
- rubric
- structured output schema
- post-validation rules
- Evidence representation materially affecting reasoning
- sampling/reasoning settings where behavior changes materially

Preferred flow:

```text
Proposed evaluator change
→ contract tests
→ benchmark / gold-set comparison
→ hard-violation check
→ semantic quality / stability comparison
→ latency/failure/cost review
→ approval
→ deploy
→ monitor
→ rollback path retained
```

Record:

- reviewer version
- prompt/rubric version
- model/provider where applicable
- benchmark dataset/rubric version
- known limitations

Do not silently replace a model and assume evaluator quality is unchanged.

---

# 9. Benchmark and corpus governance

Evaluation fixtures/corpora should identify provenance and intended use.

Possible sources:

- synthetic authored fixtures
- public examples with compatible usage rights
- consented/de-identified representative structures where appropriate
- production/runtime failures promoted into regression cases only under suitable privacy handling

Expert gold annotations should preserve legitimate disagreement rather than force false certainty.

A benchmark result must name the dataset/rubric/version it refers to.

---

# 10. Runtime evidence governance

Runtime evidence is opt-in/imported evidence unless a future explicitly specified integration says otherwise.

Before ingestion, define:

- source adapter
- fields collected
- sensitive-data handling/redaction
- workflow/revision correlation
- retention
- user deletion/export
- whether raw traces or normalized summaries are stored
- provider transmission, if any

Runtime-specific observations must not automatically become universal static rules.

---

# 11. Team / enterprise governance triggers

Before shared workspaces or enterprise governance, define:

- ownership of project/workflow artifacts
- member access model
- role/permission semantics
- organization export/deletion boundaries
- audit-history scope
- policy visibility
- provider/BYO-provider data path

Do not infer enterprise-grade confidentiality from ordinary single-user storage.

---

# 12. Data change review checklist

Any packet changing data collection/storage/provider flow must answer:

1. What new data is collected/generated?
2. Why is it necessary?
3. Where is it stored or transmitted?
4. How long is it retained?
5. Can the user export/delete it?
6. Does it contain workflow/source/runtime content?
7. Does analytics receive any part of it?
8. Does a third-party AI/service receive it?
9. Are secrets or sensitive values excluded?
10. What migration/backward-compatibility consequences exist?

If the answers are unclear, the packet is not implementation-ready.
